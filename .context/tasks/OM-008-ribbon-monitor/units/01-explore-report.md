## Answers

### 1. Bitshifter

- **What it does to ribbons.** Widens the Ribbon Reader and Writer bit selector from 4 to **31 bits** (`BitshifterMod.Bits = 31`, `B/Mod.cs:12`; bit 32 is the int's sign bit and the game tests with `> 0`). Postfixes on `LogicRibbonReader.GetBitDepth` / `LogicRibbonWriter.GetBitDepth` return `Bits` (`B/Patches.cs:12-28`). It swaps the two buildings' kanims through `CreateBuildingDef` postfixes (`B/Patches.cs:126-142`, `Display.UseAnim` 69-76), replaces `UpdateVisuals` of both with prefixes that return false (`B/Patches.cs:147-173`) and widens the NOT gate's `& 15` mask by transpiler (`B/Patches.cs:178-196`). Also an `OverlayLabelGuard` for Better Automation Overlay (`B/OverlayLabelGuard.cs`).
- **How a ribbon value is carried.** A ribbon is one int on the network: `LogicCircuitNetwork.OutputValue` (property `outputValue`); `LogicCircuitNetwork.IsBitActive(int bit)` is `(OutputValue & (1 << bit)) > 0`, the static overload `IsBitActive(bit, value)` the same on a given value. A building's port value: `LogicPorts.GetInputValue(HashedString portId)` returns `LogicEventHandler.Value` (the full int); `GetOutputValue(portId)` returns the `LogicEventSender`'s value. Bit index is 0-based in all game code; the mod displays `selectedBit + 1` (`B/Patches.cs:110-111`, glossary "Bit 0" row).
- **Reading a whole ribbon (for the monitor).** Two ways, both used by vanilla: (a) subscribe to `LogicValueChanged` (event id `-801688580`) and read `logicValueChanged.newValue` when `portID` is the input port (`LogicRibbonReader.OnLogicValueChanged`, `LogicRibbonWriter.OnLogicValueChanged`); (b) poll in `Render200ms` (`IRender200ms`) via `ports.GetInputValue(PORT_ID)`. Per bit: `LogicCircuitNetwork.IsBitActive(bit, value)`. Network of a port: `ports.GetPortCell(id)` then `Game.Instance.logicCircuitManager.GetNetworkForCell(cell)` (null = nothing wired), as in `B/Patches.cs:55-60`.
- **Does Bitshifter add a building today?** No. "It adds no buildings of its own" (`mods/bitshifter/.context/domains/entities.md`, Overview `blk-88f758ea7235`); it ships two re-drawn kanims for vanilla buildings (`src/Bitshifter/anim/assets/bitshifter_ribbon_reader|writer/`).
- **Mod.cs at load.** `BitshifterMod : UserMod2` (`B/Mod.cs:9`). `OnLoad` only logs and deliberately does **not** call `base.OnLoad` (so no `PatchAll`) (`B/Mod.cs:38-43`). `OnAllModsLoaded` runs `OverlayLabelGuard.Apply(harmony)` always, then `WhyYield(mods)`; if it returns a reason it logs "Disabled: ..." and **returns without `PatchAll`** (`B/Mod.cs:45-56`). `WhyYield` (`B/Mod.cs:58-82`) yields to an enabled mod with Workshop id `3244925649` or staticID `OniSmallCpu` (Digital CPU, `B/Mod.cs:18-26`), and to any mod that already has a Harmony owner on `GetBitDepth` or `OnSpawn` of `LogicRibbonReader` / `LogicRibbonWriter` (`B/Mod.cs:30-36`, 75-80). Consequence for a building in Bitshifter: an `IBuildingConfig` class is found by reflection over all types (`GeneratedBuildings.LoadGeneratedBuildings`, instantiates every non-abstract `IBuildingConfig`), independent of Harmony, so it registers even while the mod stands down; anything done with `[HarmonyPatch]` (plan screen, tech tree, side screen) does not apply when `PatchAll` is skipped. Whether the monitor should exist when Bitshifter yields to Digital CPU (32-bit ribbons) is a design question: the monitor shows 31 bits and would be wrong on a 32-bit ribbon.

### 3. Vanilla analogues

- **Ribbon Reader / Writer art.** Per-bit state is shown by tinting bloom symbols with `KBatchedAnimController.SetSymbolTint(symbol, colorOn|colorOff)`; colours `colorOn = (0.341, 0.725, 0.369)` green, `colorOff = (0.953, 0.290, 0.278)` red (`LogicRibbonReader` fields, `UpdateVisuals`). Symbols `bit1_bloom`..`bit4_bloom` and `output_light_bloom` are tinted; the **selected-bit highlight is a pose** chosen by `kbac.Play(num + "_" + (selectedBit + 1))` where `num` counts wired ports (4 for ribbon, +1 for 1-bit) (`LogicRibbonReader.UpdateVisuals`, `LogicRibbonWriter.UpdateVisuals`). Kanim list of `logic_ribbon_reader` (via `kanim.py list`): symbols `bit1..bit4`, `bit1_bloom..bit4_bloom`, `output_light(_bloom)`, `selected`, `reader_*`, `place`, `ui`; anims `idle`, `1`-`4`, `0_1`..`5_4`, `place`, `ui`. Refresh by `Render200ms` and on `LogicValueChanged`.
- **Ribbon wire display.** `LogicRibbonDisplayUI.SetContent(network)` colours four `Image`s with `network.IsBitActive(i) ? logicOn : logicOff`, 4 bits hard-coded (`bitDepth = 4`); the ribbon wire's own art uses symbols `wire1`..`wire4` (`OverlayModes.Logic`, `RIBBON_WIRE_1_SYMBOL_NAME`..`4`). No vanilla display shows more than 4 bits.
- **Other logic buildings.** `PixelPack` tints four symbols per colour setting (`PixelPack.cs` `SetSymbolTint`, 4 pixels). `LogicCounter` plays anims `on_<n>` and uses a `MeterController` on `meter_target` (`LogicCounter.UpdateMeter`). The repo's sensor mod follows the same meter pattern (`MultichannelCritterSensor.cs:430-448`).
- **Hover tooltip / status text.** Vanilla has **no ribbon-value text**. In the logic overlay `SelectToolHoverTextCard` draws for the port under the cursor an input/output title and two lines, active/inactive description, highlighting the line by `value == 1` / `value == 0` (`SelectToolHoverTextCard.OnSetup` logic branch); for a ribbon value above 1 neither line is selected. Outside the overlay the hover card lists the selectable's status items (`SelectToolHoverTextCard`, `GetStatusItemGroup()` loops). So a per-bit tooltip for the monitor is custom: the cheapest way is a `StatusItem` (`new StatusItem(id, name, tooltip, icon, IconType, NotificationType, allow_multiples, render_overlay, ..., resolve_string_callback)`) added with `KSelectable.SetStatusItem(category, item, data)` whose resolve callback formats the 31 bits; the repo uses `selectable.SetStatusItem(Db.Get().StatusItemCategories.Power, item)` with vanilla items (`MultichannelCritterSensor.cs:454`, `SmartWeightPlate.cs:289`) and has no custom `StatusItem` yet (grep `new StatusItem` finds none). The side screen is another route (Bitshifter's own `B/SideScreen.cs` shows how it patches one).
- **Cheapest correct way to drive 31 independent lamps.** One symbol per lamp, toggled with `SetSymbolVisiblity` or tinted with `SetSymbolTint`, exactly like the vanilla bit lights and Bitshifter's own 14 `seg_*` symbols (`B/Patches.cs:114-123`). `GetSymbolVisiblity` gives the state back for tests; the kanim symbol limit is `maxSymbolsPerBuild` of the batch group (the prototype's 31 + 6 symbols is far below Bitshifter's 40+ already in use on the reader). Per-lamp overlay anims would need a controller per lamp and are not needed. The prototype is built for this (see "Prototype kanim").
- **Size and ports.** Ribbon Reader and Writer are **2 x 1** (`CreateBuildingDef(ID, 2, 1, ...)`); Reader: ribbon input `CellOffset(0,0)`, 1-bit output `CellOffset(1,0)`, `InitialOrientation = R180`, `PermittedRotations.R360`; Writer: 1-bit input `(0,0)`, ribbon output `(1,0)`, rotatable (`LogicRibbonReaderConfig`, `LogicRibbonWriterConfig`). Counter 1x3, Memory 2x2, Switch/Alarm 1x1, PixelPack 4x1. A 2 x 2 monitor (prototype size) with a ribbon input at one edge cell is within range.

## Addendum: switch-mode design input (no decisions)

Input: lamp symbols are white on purpose (tinted at runtime); the Monitor has a ribbon input and a ribbon output; output connected = 31-channel switch the player sets; both connected = lamp green for "incoming bit on", purple for "switch on". The white lamps fit tinting, so Art request item 4 is answered: tint, not hide/show (item 3, the unlit socket under each lamp, still needs the png). The prototype has one lamp symbol per bit, so green and purple are two tint colours of one symbol; a bit that is both incoming-on and switch-on needs a third rule (design decides).

- **Runtime tint.** `KBatchedAnimController.SetSymbolTint(KAnimHashedString symbol, Color color)` looks the symbol up in the batch group's build and writes `SymbolInstanceGpuData.SetSymbolTint(symbolIndex, color)` (skipped when unchanged, then marks dirty) (build 744825). It is per symbol, so 31 lamps take 31 colours. Vanilla and Bitshifter call it on every refresh (`Render200ms` and on `LogicValueChanged`), before `Play(pose)` (`LogicRibbonReader.UpdateVisuals`; `B/Patches.cs:105-108`), so a tint set before a `Play` is relied on to survive anim changes: the data belongs to the controller, not the anim. It is not saved: the controller creates `new SymbolInstanceGpuData(maxSymbolsPerBuild)` with default `Color.white` (`KBatchedAnimController`, setup), and nothing restores it after load, so the component re-applies tints in its first refresh after `OnSpawn`, as the reader does. Not verified in game: a tint set in the same frame as a pose change (vanilla's pattern suggests it survives). Bloom lamps glow in their tint colour. Visibility is separate state (`hiddenSymbolsSet`).
- **Is a port connected.** `LogicPorts.IsPortConnected(HashedString portId)` = `Game.Instance.logicCircuitManager.GetNetworkForCell(GetPortCell(portId)) != null` (`LogicPorts.cs:462-466`); `GetPortCell(id)` returns -1 for an unknown id (Bitshifter guards it, `B/Patches.cs:55-60`). `LogicPorts.GetConnectedWireBitDepth(portId)` (`LogicPorts.cs:482`) says which wire is on the port (`LogicWire.BitDepth`: one-bit vs ribbon); the Ribbon Reader reads the wire object on its output cell (`Grid.Objects[portCell, 31]`, `LogicWire.MaxBitDepth`) to decide between a shifted ribbon and a single bit (`LogicRibbonReader.UpdateLogicCircuit`). Gates use `LogicGate.GetPortConnected(PortId)` (`LogicGate.cs:699`); the hover card shows the "wire missing" state via `IsPortConnected` and the port flag `show_wire_missing_icon: true`.
- **Unconnected port, vanilla behaviour.** The Ribbon Writer does not check: `UpdateLogicCircuit` always calls `SendSignal(OUTPUT_PORT_ID, currentValue << selectedBit)`, and `LogicPorts.SendSignal` sets the value on the port's `LogicEventSender` with or without a network (`LogicPorts.cs:387-402`), so the value waits until a wire is attached. Pose and tint react only when `GetNetworkForCell` is non-null (the `num` counter in `UpdateVisuals`). An unconnected input reads 0. Output values are saved by `LogicPorts` (`serializedOutputValues`, `LogicPorts.cs:79, 224-239, 541-553`).
- **Two ribbon ports on one building.** In `CreateBuildingDef`: `def.LogicInputPorts = new List<LogicPorts.Port> { LogicPorts.Port.RibbonInputPort(INPUT_ID, new CellOffset(x, y), desc, active, inactive, show_wire_missing_icon: true) }` and `def.LogicOutputPorts = new List<LogicPorts.Port> { LogicPorts.Port.RibbonOutputPort(OUTPUT_ID, new CellOffset(x, y), ...) }` (`LogicPorts.cs:53-60`). Each port has its own `HashedString` id, a cell offset relative to the origin (rotated with the building) and its own three strings. Vanilla pair: Reader input (0,0), output (1,0) (`LogicRibbonReaderConfig`); the sensor mod has one ribbon output at (0,0) (`MultichannelCritterSensorConfig.cs:33`). Any two distinct cells of a 2 x 2 footprint work. The artist's labels do not rotate, so the building should be unrotatable, which also fixes the cells in screen space.
- **Per-bit toggle UI.** Options:
  - `ICheckboxListGroupControl` + vanilla `CheckboxListGroupSideScreen`: the building implements `Title`, `Description`, `GetData()` (`ListGroup[]` of `CheckboxItem { text, tooltip, isOn }`), `SidescreenEnabled()`, `CheckboxSideScreenSortOrder()`; the vanilla screen is chosen automatically (`IsValidForTarget`). No UI code, but the click callback is group-level (`ListGroup.onItemClicked`, an `Action` without an index), so the changed item must be found by diffing state or one group per bit. Not confirmed in detail.
  - Vanilla `LogicBitSelectorSideScreen`: one `MultiToggle` row per `GetBitDepth()` with a state icon coloured `logicOnText` / `logicOffText` (`RefreshToggles`); Bitshifter already patches it into a scroll view (`B/SideScreen.cs:16`, `SetTarget` postfix). It selects one bit, so for 31 independent switches it is a model for rows, not a reuse.
  - Custom `SideScreenContent` with PLib (repo pattern): registered by `PUIUtils.AddSideScreenContent<T>()` in a `DetailsScreen.OnPrefabInit` postfix (`multichannel-critter-sensor/.../Patches.cs:39-46`, `smart-weight-plate/.../Patches.cs:41-44`; classes `MultichannelCritterSensorSideScreen : SideScreenContent, IRender200ms` and `SmartWeightPlateSideScreen`, with `IsValidForTarget`, `GetTitle`, `SetTarget`). - **Saving the switch state.** Components use `[SerializationConfig(MemberSerialization.OptIn)]` with `[Serialize]` per saved field (`LogicRibbonWriter`: `[Serialize] public int selectedBit; [Serialize] private int currentValue;`; `LogicSwitch`, `Switch.cs:16`). ## Addendum 2: decisions on blending and the switch UI

- **Tint rules (user).** Both ports connected: output = input OR switches; lamp green for input bit on, purple for switch on, purple wins. Output only: switches shown purple. Mapping to code: per bit `SetSymbolTint(bit_bloom_N, switchOn ? purple : inputOn ? green : off)`; "off" colour is not a tint of white lamps unless it is a dark colour, so decide between a dark tint (lamp visible dark grey) or `SetSymbolVisiblity(false)` for off (the socket is already drawn in the body, so hiding the lamp is the natural off state). Output value = `inputValue | switchedBits` sent with `LogicPorts.SendSignal(OUTPUT_ID, value)` on `LogicValueChanged` of the input and on every switch change (the Writer does the same on both events, `LogicRibbonWriter.OnLogicValueChanged`, `SetBitSelection`).
- **Grid side screen of 31 toggles matching the 8 x 4 face: feasible with PLib.** PLib 4.25.0 (the version the repo uses, `common/oni-mod.targets:75`) contains `PGridPanel`, `PToggle`, `PCheckBox`, `PButton`, `PPanel`, `PLabel`; I listed the types from `~/.nuget/packages/plib/4.25.0/lib/net48/PLib.dll`. The repo already builds PLib side screens: `SmartWeightPlateSideScreen` (`PPanel` root with `PLabel` and `PCheckBox` `AddTo(gameObject)`, `EnsureBuilt`, `PCheckBox.SetCheckState`, `smart-weight-plate/.../SmartWeightPlateSideScreen.cs:60-95`), `MultichannelCritterSensorSideScreen` (species check lists and a cloned vanilla threshold block, lines 247, 681) and `UpgradePlanner/UI/MaterialTabView.cs` (`PCheckBox` lists). No mod in the repo uses `PGridPanel` or `PToggle` yet, so a grid is new ground but the same API: `new PGridPanel("Bits")` with 8 columns and 4 rows (`AddColumn`/`AddRow`, `AddChild(child, new GridComponentSpec(row, col))`), each cell a `PToggle` or a `PButton` whose state is the bit; spare cell left empty or a ribbon mark. Cost: the PLib setup Bitshifter lacks today (`<UsePLib>true</UsePLib>`, `PUtil.InitLibrary(false)` in `OnLoad`, ILRepack merge into the mod DLL, which `oni-mod.targets` does for PLib mods), a `SideScreenContent` subclass with `IsValidForTarget` on the monitor component, `GetTitle`, `SetTarget`, `Render200ms` to refresh the state, registration by `PUIUtils.AddSideScreenContent<T>()` in a `DetailsScreen.OnPrefabInit` postfix (`Patches.cs` in both sensor mods), strings for the title and toggle tooltips, and a layout pass (side screen width: Bitshifter already clamps layout to the 280 px details panel, `B/SideScreen.cs`; eight columns in 280 px leaves about 30 px per toggle). The grid's per-bit labels and on/off look (`PToggle` sprites, `PUITuning` styles) are not read in detail. The interaction model (click toggles a bit) maps one-to-one to the screen; a hover tooltip per cell is available through `ToolTip`. Tests: layer 0 can call the component's setter; a layer 1 click needs a UI click helper that TestRunner does not have (harness gap: `Kit/Tools.cs` drives world tools only; no side-screen click helper was found).
- **Fallback: a Ribbon Reader/Writer-style bit selector allowing several bits on. Cheap, no UI code.** The vanilla `LogicBitSelectorSideScreen` is valid for any target with `ILogicRibbonBitSelector` (`IsValidForTarget`, `SetTarget`), builds one row per `GetBitDepth()` and on click calls `target.SetBitSelection(bit)` then `UpdateVisuals()` (`SelectToggle`). Each row's state icon and text come from `target.IsBitActive(bit)` every tick (`UpdateStateVisuals`); only the row highlight (`ChangeState(0)`) follows `GetBitSelection()`. So the monitor component implements `ILogicRibbonBitSelector` with `GetBitDepth() = 31`, `SetBitSelection(bit)` = **toggle that bit** in `switchedBits`, `GetBitSelection()` = the last toggled bit, `IsBitActive(bit)` = switch on (or input on, design call), `GetInputValue`/`GetOutputValue` from its ports, `SideScreenDisplayReaderDescription()`/`WriterDescription()` both false to hide the vanilla description blocks, `SideScreenTitle` a string key, and `UpdateVisuals()`. Bitshifter's existing scroll-view postfix (`B/SideScreen.cs:16`) then applies unchanged, so 31 rows scroll. Limits: single list not a grid, one row highlight, the vanilla row texts say "Bit n" and on/off text from vanilla strings (`UI.UISIDESCREENS.LOGICBITSELECTORSIDESCREEN`), the title is read from `titleKey` as a STRINGS key. No PLib needed. Risk: the highlight shows one row as selected, which can read as "only this one" (could be mitigated by always returning the lowest on bit or -1). Not run in game.
- **Gaps added.** `PGridPanel`/`PToggle` API surface and look not inspected in the DLL beyond type names; whether a 31-toggle grid fits the side screen height; a side-screen click helper in TestRunner (none exists).
