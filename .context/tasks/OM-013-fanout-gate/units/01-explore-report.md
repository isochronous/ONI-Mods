## Summary for the plan

1. The art is complete and consistent, with ONE defect and ONE naming mismatch: (a) every anim frame has NaN bounds (the same export habit as the Diagnostic Panel's, which `tools/make_art.py` fixes); (b) the game names the kanim from the FOLDER, so the building must use `fanout_gate_kanim`, while the build/anim files say `logic_fanout`. Repo convention is folder = file base = build name.
2. The footprint the art implies is **3 x 1** (not 2 x 1), ports at `CellOffset(-1,0)` (1-bit input) and `CellOffset(1,0)` (ribbon output). I could not prove it from the art alone; see Open questions.
3. Toolkit pattern: copy the Diagnostic Panel's four files and add one row to `Toolkit.Buildings`. No new patch classes are needed for build menu, tech, strings.
4. Side screen: the vanilla `LogicBitSelectorSideScreen` CAN be reused for multi-select by implementing `ILogicRibbonBitSelector` on the gate (toggle the bit in `SetBitSelection`) plus one small Harmony postfix on the private `RefreshToggles` to light every selected row. Cheapest route, no UI code. Risks listed below. The fallback is a copy of the Diagnostic Panel's PLib grid (already tested), which OM-008 chose for its 31 switches.
5. Gate output: `ports.SendSignal(OutputPort, inputOn ? mask : 0)`, same call the vanilla Ribbon Writer uses.

## 1. The art (fanout_gate)

Files: `A/anim/assets/fanout_gate/logic_fanout_0.png` (512 x 512), `logic_fanout_anim.bytes`, `logic_fanout_build.bytes`. Untracked in git (git status `?? mods/bitshifter/src/Bitshifter/anim/assets/fanout_gate/`).

Commands: `python common/tools/Kanim/kanim.py list <folder>`, `dump <folder> --anim <name>`, `render <folder> <out.png> --anim <name> --scale 0.5`; plus a small script (scratchpad `ext.py`) using `kanim.load/read_build/read_anims` to compute each anim's extent.

**Build (kanim.py list / read_build):** build name `logic_fanout`. Symbols:
- `light_off` 1 frame, 64 x 68: the dark unlit lamp.
- `light_bloom` 2 frames, 64 x 68, carries the bloom flag: frame 0 is the green lamp, frame 1 the red lamp (colours are baked into the texture; the on_* anims show them straight, `on_1_1010` render: green/red/green/red lamps, green input lamp).
- `panel` 236 x 528: the body, stored on its side and rotated 90 degrees by every anim (matrix `-0 -1 1 -0`).
- `place` 236 x 528: the white construction outline (render over a dark background shows the same body outline; 7516 opaque white pixels).
- `ui` 284 x 244: build menu icon, the body drawn octagonal in perspective on a plain shadow, like vanilla icons (`units/01-art/fanout-ui.png`).

**Anims (35), all 1 frame at 30 fps:**
- `off`: input lamp and all four output lamps are `light_off` (dark). For nothing wired / inactive.
- `on_<i>_<bbbb>` for i in {0,1} and every one of the 16 four-bit patterns (0000 to 1111; I checked the full set is present: 32 anims). Each shows the input lamp and the four output lamps as `light_bloom` frame 0 (green) or 1 (red). From the dump: in `on_1_0000` the input lamp (x -104.7) is frame #0 (green) and all four output lamps #1 (red); in `on_0_1010` the input lamp is #1 (red). So `<i>` is the input lamp: 1 = green (input on), 0 = red. `<bbbb>` reads top to bottom: in `on_1_1010` the top lamp (y -160.8) is green, then red (-122.7), green (-84.8), red (-47.1). Which gate bits the four lamps stand for is not in the art (see Open questions).
- `place`: the `place` symbol only. `ui`: the `ui` symbol only.

**Positions (anim units, 200 per cell, y negative is up, anim origin x=0 is the centre of an odd-width footprint; check: the 2 x 2 Diagnostic Panel body spans x -213..213, the vanilla 2 x 2 AND gate x -199..203):**
- panel/place: x -263..265, y -218..18 (528 x 236). The body is centred on x=0 and one cell tall (a 1-cell building overhangs by 18 each way; the vanilla Ribbon Writer's `place` is 364 x 223 for a 2 x 1).
- input lamp (`light_*` at 1.0 scale) centre (-104.7, -102.7), and the input arrow drawn in the panel at about x -167 (render: arrow left of the lamp).
- four output lamps (0.5 scale) at x 116.9, y -47.1 / -84.8 / -122.7 / -160.8; their four small arrows at about x 151 (render).
- Centre of the output lamp column in y is -104, level with the input lamp: both read as sitting on the one cell row.
- ui: x -146..138.

**Size in cells.** Width 528 at 200 per cell is 2.64 cells; a symmetric body centred on x=0 only fits an odd width, so 3 cells (600), body at 88 percent of the footprint, which is what the Ribbon Writer does (364 of 400 = 91 percent). Height 236 is one cell. A 2-cell footprint would let the body overhang the footprint by 63 units on each side (the Diagnostic Panel overhangs by 13). So the art says **3 x 1**. The one detail that points the other way: the lamps sit at x -105 and +117, which are the cell centres of a 2-wide building (+-100), not of a 3-wide one (-200, 0, 200). With 3 x 1 the input wire reaches the body at x -200 and the arrow at x -167 is the entry mark just inside it, and the output arrows at x 151 point out toward x 200. I read it as 3 x 1 with lamps drawn inboard of the ports.

**Compared with the Diagnostic Panel and vanilla gates:**
- Nothing is tinted at runtime in the gate art (bits and the input are baked into 32 poses), unlike the Diagnostic Panel (31 symbols tinted by `SetSymbolTint`) and the vanilla Ribbon Writer (`bit1_bloom` etc. tinted, `LogicRibbonWriter.cs:42-50`, 189-199). Code just plays `on_<i>_<bbbb>`; no tint, no `SetSymbolVisiblity`.
- No `meter`, `selected`, digits or text: nothing in the art shows the configured bits (the side screen does). Nothing rotates in the art except the whole body, so the building could be rotatable (vanilla gates and the Ribbon Writer are R360, `LogicRibbonWriterConfig.cs:177`; the Diagnostic Panel is `Unrotatable` because of its digits, `RibbonDiagnosticPanelConfig.cs:28`). Open question.
- Frame bounds: `dump` prints `bounds nan, nan  nan x nan` for every anim of `fanout_gate`; the Diagnostic Panel's shipped copy prints real bounds (`-0.0, -200.0  426.0 x 426.0`). `tools/make_art.py:build_panel` (lines 334-358) exists to fix exactly this from the artist's export in `anim-original/diagnostic_panel` (docstring lines 31-37). The gate needs the same: put 3GuB's export in `mods/bitshifter/anim-original/fanout_gate/` and extend `make_art.py` (and `--check`) to write `src/.../assets/<folder>` with bounds computed. The OM-008 explore report (`.context/tasks/OM-008-ribbon-monitor/units/01-explore-report.md:24`) noted a shipped sensor kanim with NaN bounds works in game, so this is a consistency fix, not a known crash.
- Naming. `KMod.Mod.LoadAnimation` (Mod.cs:709-765 of the decompile) names each kanim `directoryInfo.Name + "_kanim"` and reads any `*_anim.bytes`, `*_build.bytes` and `.png` in the folder, whatever their base name (lines 738-749, 759). So the folder `fanout_gate` gives `fanout_gate_kanim`; the building def must say `"fanout_gate_kanim"`, and `logic_fanout` appears nowhere in code. Every other asset in the repo has folder = file base = build name (bitshifter_ribbon_reader, diagnostic_panel, critter_sensor_advanced, ...). Recommendation: keep the folder `fanout_gate`, rename the three files to `fanout_gate_*` and the build's internal name to match when it goes through `make_art.py` (the tool's `write_kanim` takes a name); or rename the folder to `logic_fanout`. No collision either way: no vanilla kanim `logic_fanout` (`kanim.py list logic_fanout` finds none) and no Workshop mod contains `FanoutGate`, `FanOutGate`, `LogicFanout`, `fanout_gate`, `logic_fanout` (grep over F:\SteamLibrary\steamapps\workshop\content\457140, dll/yaml/cs/json/po).

## 3. Side screen: reuse the vanilla screen with multi-select

**Vanilla `LogicBitSelectorSideScreen`** (decompile `LogicBitSelectorSideScreen.cs`, interface `ILogicRibbonBitSelector.cs`):
- Valid for any object with the interface: `IsValidForTarget` -> `target.GetComponent<ILogicRibbonBitSelector>() != null` (73-76). The interface is used only by `LogicRibbonReader`, `LogicRibbonWriter` and this screen (grep over the whole decompiled assembly: those four files).
- Members the gate must implement: `SideScreenTitle`, `SideScreenDescription`, `SetBitSelection(int)`, `GetBitSelection()`, `GetBitDepth()`, `SideScreenDisplayWriterDescription()`, `SideScreenDisplayReaderDescription()`, `IsBitActive(int)`, `GetOutputValue()`, `GetInputValue()`, `UpdateVisuals()` (interface 3-25).
- `SetTarget` (78-100): `titleKey = target.SideScreenTitle` (a STRINGS key string, like `"STRINGS.UI.UISIDESCREENS.LOGICBITSELECTORSIDESCREEN.RIBBON_WRITER_TITLE"` in `LogicRibbonWriter.cs:52`, so the gate's key should be a path under `ModStrings`, e.g. `"STRINGS.BITSHIFTER.FANOUTGATE.SIDE_SCREEN_TITLE"`); sets the reader/writer description containers from the two Display methods (92-93; the description text itself comes from the prefab, `SideScreenDescription` is not read by the screen), so the gate returns false for both to hide them; then `RefreshToggles()`.
- Row click: `SelectToggle(bit)` (34-39) = `target.SetBitSelection(bit); target.UpdateVisuals(); RefreshToggles();`. Every call of `RefreshToggles` re-binds each row's `onClick` to `SelectToggle(i)` (55-59).
- Row look: `RefreshToggles` (41-71) creates a row per `i < target.GetBitDepth()` and never removes any (46-54: `toggles_by_int` keeps them across targets); the "selected" look is `MultiToggle.ChangeState(0)` for the row where `target.GetBitSelection() == key`, state 1 for every other (60-70). So the vanilla screen highlights exactly one row. Each tick (`RenderEveryTick` 102-113 -> `UpdateStateVisuals` 127-132) the row's state icon colour and "Active/Inactive" text follow `target.IsBitActive(bit)`; this does not touch the highlight.
- Bitshifter's existing patch `LogicBitSelectorSideScreen_SetTarget_Patch` (`A/SideScreen.cs:16-37`) wraps the row list in a scroll view once, and `FitUnderHeader` clamps widths; it works on any target of the screen, the gate included. It is uncategorized, so it is applied only when the mod does not yield (`Mod.cs:62`).

**Route (cheapest, no UI code):**
1. `FanoutGate : KMonoBehaviour, ILogicRibbonBitSelector, IRender200ms` with `[Serialize] int mask`. `GetBitDepth()` = `BitshifterMod.Bits` (31). `SetBitSelection(bit)` toggles that bit in `mask`, then re-sends the output; `GetBitSelection()` returns the lowest set bit or -1 so the vanilla single-highlight is harmless; `IsBitActive(bit)` = the output ribbon carries the bit (as `LogicRibbonWriter.IsBitActive`, 150-159) or the mask has it (design call); `GetInputValue()` = the 1-bit port's value, `GetOutputValue()` = `ports.GetOutputValue(OutputPort)`; both Display*Description() false.
2. A postfix on the private `LogicBitSelectorSideScreen.RefreshToggles` (`[HarmonyPatch(typeof(LogicBitSelectorSideScreen), "RefreshToggles")]`, `___target` and `___toggles_by_int` injected): when the target is a `FanoutGate`, `ChangeState(mask has bit ? 0 : 1)` for every row. `RefreshToggles` runs on both `SetTarget` and `SelectToggle`, so the highlight is right on open and after each click. It must be `[HarmonyPatchCategory(Toolkit.PatchCategory)]`, and so must the scroll-view patch if the gate is to scroll under Digital CPU (today that patch is uncategorized, `SideScreen.cs:16`; it could be moved to the toolkit category, which changes nothing for Reader/Writer because it is a SetTarget postfix on the screen, but it would then also apply to Reader/Writer while Bitshifter yields to Digital CPU, which is a behaviour change to decide on).
3. Copy-settings via `CopyBuildingSettings` + `-905833192` handler copying the mask (as the panel, `RibbonDiagnosticPanel.cs:163-168`).

**Risks of the vanilla-screen route:**
- The row list is shared with Reader and Writer and keeps the rows it has made. If the first target of the session was a Digital CPU reader (depth 32), the gate's list shows a 32nd row; `SetBitSelection(31)` must be ignored (bit 32 is the sign bit; `BitshifterMod.Bits` comment, `Mod.cs:13`).
- No place for a hint line ("send these bits while the input is on") or an All off button: the vanilla prefab has only the two description containers (reader/writer) which show fixed vanilla text. Anything extra needs a patch that adds a LocText/button to the screen, or a header string. Today the title is the only text the gate can supply.
- The row's state text reads Active/Inactive from `IsBitActive` which, if defined as the output network's bit, is Inactive while the input is off, even for selected bits: that is correct for the vanilla look but may read oddly beside the highlight. The highlight (state 0/1) is the only selection mark.
- `RefreshToggles` is private; the patch is on a vanilla private method (stable across the U59/U60 builds Bitshifter ships on; `LogicBitSelectorSideScreen_SetTarget_Patch` already relies on `rowPrefab` and `SetTarget`). A game change to the screen breaks only the gate's multi-highlight, not Reader/Writer.
- Mods that patch the same screen (e.g. Better Automation Overlay, already known to NRE with Bitshifter via `OverlayLabelGuard`) see a target that is not a Reader/Writer; not checked.

**Fallback:** the Diagnostic Panel's PLib grid (`RibbonDiagnosticPanelSideScreen.cs`): 8 x 4 buttons, Hint, All off, tested (`DiagnosticPanel.cs:277-386`). OM-008's design report chose it over the list for 31 independent switches; the user now asks for the Reader/Writer list, so I recommend the vanilla route first and the grid only if the rows read badly in game. A custom row list in PLib would be the most work and is not needed.
